# 06 · 泛化分析：这套加速对 sherpa 上百个模型都有效吗？

## 6.0 短答

**机制与模型族无关（它在 API 层），但幅度强依赖模型/硬件/批量组成。**
不是"所有模型都提速 2.5×"，合理预期是：

| 场景 | 预期加速 |
|---|---|
| CPU，4–8 逻辑核，batch 8，时长不均（本实验） | **2.0–3.0×** |
| CPU，核数 ≥ batch，模型解码较重（transducer/AED） | 2.5–4×（需实测） |
| CPU，batch 1 或时长均匀 | 1.0–1.4×（只吃并发，不吃 padding/LPT） |
| GPU 上跑 | 通常 **≈1.0×，甚至 <1**（不要照搬） |
| 流式/online 模型 | 路径不同，需改写 adapter，不能直接套 |

## 6.1 为什么"机制"是模型无关的

三个收益来源都发生在**调用方式**上，不在模型内部：

1. **去 padding**：`decode_streams` 把整批 pad 到最长；`decode_stream` 不 pad。
   凡是用这套 `OfflineRecognizer` API 的模型，都有这个入口差异。
2. **并发**：ORT `Run` 释放 GIL，N 个 `num_threads=1` 的 session + N 个 worker，
   与模型是 CTC、transducer 还是 AED 无关——只与"每帧的 CPU 工作量"有关。
3. **LPT 派发**：任务代价 ∝ 音频时长，与模型无关。

所以结构上，它对 sherpa 全家族（Zipformer/Transducer、Paraformer、SenseVoice、Whisper、
NeMo CTC、多语 Conformer 等）都**可复用**。这就是它比"针对 FunASR 写个优化"更通用的原因。

## 6.2 但幅度由 5 个变量决定

| 变量 | 影响 | 本实验取值 |
|---|---|---|
| padding 比 P = 批内 pad 后帧数 / 真实帧数 | 直接乘在收益上 | ~1.25–2.0（batch 8，时长差 8 倍） |
| 核数 / stock 线程数 | 并发收益上限 | 4 逻辑核 / 2 线程 = 2 |
| 物理核 vs SMT | 4 个 SMT 线程只有 ~2× 单线程，不是 4× | 2 物理核 |
| 前端占墙钟比 | 可否被流水线隐藏（本实验 9%） | 2.6–4.5%（step1）→ 9%（并发后占比上升） |
| 解码器 CPU 占比 | CPU 端的循环（transducer joiner）越重，并发收益越大 | CTC，很轻 |

一个可用的粗估式（已用本实验校准）：

```
speedup ≈ P × min(workers, batch, 有效并行度) / nt_stock × (1 + 流水线修正)
```

本机代入：`1.7 × min(4,8,~2.4) / 2 ≈ 2.0`，实测 2.5——超出的部分来自流水线与 LPT。
（"有效并行度"≈ 物理核 × 1.2，SMT 的边际收益很低；4 逻辑核实际只给 ~2.2–2.4 倍单线程。）

## 6.3 按模型族逐个判断（哪些会更明显，哪些要小心）

| 模型族 | padding 问题 | 并发收益 | 结论 |
|---|---|---|---|
| **NeMo FastConformer-CTC**（本实验） | 明显（batch 8 差 1.25–2×） | 好（编码器占 95%） | 2.5×（实测） |
| **Zipformer / Conformer Transducer** | 明显；解码循环还有 joiner 逐帧 CPU 工作 | 更好（CPU 工作量更大） | 预计 ≥ 2.5×，需实测 |
| **Paraformer / SenseVoice（NAR/AED）** | 明显 | 好（编码器重） | 预计 2–3× |
| **Whisper（sherpa 实现）** | 特殊：模型本身把音频 pad/切到 30s 窗口，**单流也有 padding**，批处理额外 padding 较小 | 好 | 主要吃并发，预计 1.5–2.5×，**必须实测** |
| **多语/大词表模型** | 与 CTC 类似 | 好，但内存带宽先饱和 | 2–3× 后进入平台 |
| **流式（online recognizer）** | 没有"整批 pad"概念 | 跨流并发仍可做 | 需新 adapter，不能直接套 |
| **GPU 上任何模型** | 无意义（GPU 已被一次前向占满） | 并发会互抢 | **不要用**，可能更慢 |

同时要提醒：**sherpa 的"上百个模型"大多是同一套 `OfflineRecognizer` 的权重变体**，
受益结构一致；但每个模型的"编码器 vs 解码器 vs 前端"占比不同，**必须逐模型重测**，
不能把本实验的 2.5× 直接写进宣传语。

## 6.4 精度上的"泛化"：会不会改变识别结果？

分两种情况：

1. **本实验（CTC + 单流路径与 stock 完全一致）**：逐字节相同，任何语言、任何数据集都不会变
   （0/119、0/112、0/48 多次核对）。
2. **其他模型**：去掉 padding 改变了数值路径，某些模型可能**文本微变**——
   例如注意力掩码/卷积 padding 会泄漏进结果，或批内 padding 影响 batch norm 类统计。
   方向通常更好（不再让模型"看"填充帧），但**不能假设零漂移**：
   仪器的 `transcript_drift` 门与配对 WER 区间正是为此存在——先测，再信。

所以"泛化能力"这件事在这里是**可验证的**，不是玄学：任何模型上，跑一次配对的 WER 区间即可判定。

## 6.5 三步判定法（换模型后 3 分钟内知道值不值得做）

1. **测 padding 比**：同一批音频，比较 `decode_streams(batch)` 与逐条 `decode_stream` 的墙钟；
   比值 > 1.1 才有第一份收益。
2. **测单线程扩展性**：`num_threads=1` 单流 vs `num_threads=2/4` 单流的墙钟；
   如果 1→2 线程只有 1.1×，说明这模型是内存带宽受限，并发收益也会打折。
3. **测前端占比**：profile 里 `frontend / wall`，>5% 说明流水线还能再赚一点。

三项都通过（padding 比高、单线程不饱和、前端有占比），再投入优化；否则收益会低于 1.5×。

## 6.6 一句话总结

- **可移植的是方法**：每流解码 + 等权并发 + 流水线 + LPT；
- **不可移植的是数字**：2.4989 是"4 逻辑核 / 2 物理核 + 这个 NeMo 模型 + batch 8 + 时长差 8 倍"的产物；
- **必须重测的对象**：任何新模型、新核数、新 batch 策略、GPU 部署。
